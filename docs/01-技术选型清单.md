# RAG 系统技术选型清单 v0.1

> 目标：FastAPI + LangChain + LangGraph + MySQL + 向量库，带登录认证、RBAC 权限、后台参数配置、知识库上传与切片配置。
> 本文用途：**给你做决策**。每节给出候选、推荐、代价。文末有 6 个必须你拍板的决策点。

## 2. 逐层选型

### 2.1 Web 框架与基础

| 候选 | 说明 | 结论 |
|---|---|---|
| **FastAPI + Uvicorn** | 异步原生、Pydantic 校验、自动 OpenAPI、SSE 天然友好 | ✅ 指定，无争议 |
| Pydantic v2 + pydantic-settings | 请求模型 + 环境配置 | ✅ 必选 |
| Granian | Rust 版 ASGI server，比 Uvicorn 快 | 可选，先不用 |

> 补充：`uv` 作为包管理器（比 pip/poetry 快一个数量级），`ruff` 做 lint/format。

---

### 2.2 关系库与 ORM

| 候选 | 说明 | 结论 |
|---|---|---|
| **MySQL 8.0 + SQLAlchemy 2.0 async + Alembic** | 异步驱动 `asyncmy`；Alembic 管迁移 | ✅ 推荐 |
| Tortoise ORM | 轻量异步，生态弱于 SQLAlchemy | 不推荐 |
| MySQL 5.7 | JSON 支持和 CTE 差 | ❌ 用 8.0 |

**关键点**：MySQL 只存元数据（用户、角色、知识库、文档、切片文本、任务、会话记录）。**切片文本建议也存 MySQL**（便于后台查看/重切），向量存向量库，用 `chunk_id` 关联。

---

### 2.3 RAG 编排：LangChain + LangGraph

| 层 | 选型 | 说明 |
|---|---|---|
| 链路组装 | LangChain（LCEL / Runnable 体系） | Loader、Splitter、Retriever、Prompt 复用 |
| 状态编排 | **LangGraph** | 把「意图识别 → 查询改写 → 多路召回 → 融合 → 重排 → 生成 → 引用校验/兜底」画成图，支持条件分支和循环重试 |
| 记忆 | LangGraph Checkpointer（MySQL/Redis Saver） | 多轮对话状态持久化 |
| 流式 | `astream_events` → FastAPI SSE | token 级流式 + 节点事件（前端可显示"正在检索…"） |

> 为什么不只用 LCEL：你需要「检索不到就改写重试」「多知识库路由」「答案引用校验失败回退」这类**带分支和循环**的逻辑，Chain 表达不了，LangGraph 才是正解。

---

### 2.4 向量库 ★ 核心决策

| 候选 | 优势 | 代价 | 适用 |
|---|---|---|---|
| **Qdrant** | Rust 单二进制，一条 Docker 命令；payload 过滤强（按知识库/权限过滤是刚需）；原生 sparse+dense 混合检索；支持标量量化省内存 | 社区比 Milvus 小；超大规模（亿级）需分片规划 | ✅ **10 万~1 亿向量首选** |
| **Milvus 2.4+** | 功能最全（多索引类型、分区、GPU 索引）；千万级以上成熟 | 依赖 etcd + MinIO + Pulsar 一整套，运维重，吃内存 | 千万级以上 / 团队已有 Milvus |
| **pgvector** | 与 PG 同库事务一致；运维零新增组件 | 你已用 MySQL，要多养一套 PG；带过滤的 top-k 性能弱于专用库；HNSW 建索引慢 | 极小规模、想少一个组件 |
| **Elasticsearch / OpenSearch** | BM25 + kNN 天然混合检索；元数据过滤和聚合最方便 | JVM 吃内存（建议 8G+）；向量只是附属能力 | 已有 ES 集群 / 检索以关键词为主 |
| Chroma | 开发体验好 | 生产不行（单机、无副本） | ❌ 仅 POC |
| 云托管（腾讯 VectorDB / 阿里 DashVector） | 免运维 | 成本、数据出域 | 无运维团队时可选 |

**我的推荐：Qdrant。** 理由：你的检索一定要带 `kb_id` / `permission_tags` 过滤（权限隔离），Qdrant 的 payload filter 是最省心的；而且它同时支持 dense + sparse，混合检索不用再引一套 ES。

### 2.5 Embedding 与 Rerank

| 用途 | 候选 | 说明 |
|---|---|---|
| Embedding | **阿里百炼 text-embedding-v4**（1024 维） | ✅ **已定版**（见 §6.5.2）：免部署、中文强、按量付费 |
| | bge-m3（1024 维） | 中英多语，自带 sparse 输出；本地跑需 GPU/CPU 算力 |
| | bge-large-zh-v1.5 | 纯中文强，1024 维，不支持稀疏 |
| | OpenAI text-embedding-3-large | 3072 维，效果好，境外 + 成本 |
| Rerank | **阿里百炼 gte-rerank-v2** | ✅ **已定版**（见 §6.5.4）：与 Embedding 同一云商，共用密钥与配额 |
| | bge-reranker-v2-m3 | 本地部署，成本 0，需显卡 |
| | Cohere Rerank 3.5 | 效果最强，境外且按次收费 |

> ⚠️ **工程铁律**：Embedding 模型和维度一旦上线就锁定。换模型 = 全量重建向量。所以要在 `knowledge_base` 表存 `embedding_model` + `dim` 字段，并且**每个知识库可独立配置**，方便灰度迁移。

### 2.6 文档解析

| 类型 | 选型 |
|---|---|
| PDF（文本型） | **PyMuPDF (fitz)** — 快、版面信息全 |
| PDF（复杂：双栏/公式/表格） | **MinerU (magic-pdf)** — 效果最好，但重（需 GPU 更佳） |
| PDF（扫描件） | **RapidOCR** 或 PaddleOCR（先判断有无文本层，无则走 OCR） |
| Word / Excel / PPT | python-docx / openpyxl / python-pptx |
| HTML / Markdown / TXT | 原生解析 |
| 统一中间格式 | **Markdown**（保留标题层级和表格），所有解析器输出 MD 再进切片器 |

> 设计要点：解析器做成**策略注册表 + 可按知识库配置**（`parser_type`），别写死 if-else。`unstructured` 可以不用——它依赖太重，效果不一定比原生库好。

### 2.7 切片（Chunking）— 需要后台可配

要落库的配置项：

```json
{
  "strategy": "recursive | fixed | markdown_header | semantic | parent_child",
  "chunk_size": 512,
  "chunk_overlap": 64,
  "separators": ["\n\n", "\n", "。", "！", "？"],
  "min_chunk_size": 80,
  "keep_table_intact": true,
  "parent_chunk_size": 2048,
  "clean_rules": ["strip_header_footer", "dedup_blank", "remove_url"]
}
```

| 策略 | 说明 | 推荐度 |
|---|---|---|
| **recursive（递归分隔符）** | LangChain `RecursiveCharacterTextSplitter`，稳定基线 | ✅ 默认 |
| **markdown_header** | 按标题层级切，保留文档结构，检索命中后上下文完整 | ✅ 强烈建议 |
| **parent_child（父子块）** | 用小块检索、用大块喂模型（small-to-big），效果提升明显 | ✅ 进阶首选 |
| semantic（语义切片） | 靠 embedding 相似度找断点，质量好但成本高、慢 | 可选 |
| fixed（定长） | 只做对照 | 不推荐 |

### 2.8 认证

| 方案 | 说明 | 结论 |
|---|---|---|
| **JWT 双 Token + PyJWT + passlib[bcrypt]** | access 15min + refresh 7d，refresh 存 Redis 可主动踢人 | ✅ 推荐（可控、无黑盒） |
| fastapi-users | 开箱即用（注册/登录/验证/重置密码/OAuth） | 想少写代码可选，但定制 RBAC 时略绕 |
| Authlib + OIDC | 接企业 SSO / 企业微信 / 钉钉 | 后续扩展 |
| Session + Cookie | 后台管理够用 | 但和 API/移动端不统一 |

**必需的安全项**：密码 bcrypt 加盐、登录失败次数限流（Redis）、Token 黑名单、验证码（可选）、接口级权限依赖注入。

### 2.9 权限（RBAC）

| 方案 | 说明 | 结论 |
|---|---|---|
| **Casbin (pycasbin) + MySQL adapter** | RBAC with domains（域=知识库/部门），改权限只改策略表不改代码；支持 ABAC 扩展 | ✅ 推荐 |
| 自研「用户-角色-权限」三表 + FastAPI 依赖 | 简单直观，20 个接口够用；多租户/细粒度就吃力 | 可用，简单场景 |
| OPA / Rego | 能力强但引入新语言和 sidecar | ❌ 过度设计 |

**权限层次建议（4 层）**：
1. 菜单/路由级（前端动态路由）
2. 接口级（FastAPI `Depends(require_perm("kb:write"))`）
3. **知识库级 ACL**（`owner` / `admin` / `editor` / `viewer`）— 这一层最关键
4. 文档级（可选，标签/密级过滤）

### 2.10 异步任务

| 候选 | 说明 | 结论 |
|---|---|---|
| **Celery + Redis** | 成熟、重试/定时/优先级齐全、Flower 可视化、支持多队列（解析队列 / 向量化队列分开，避免互相阻塞） | ✅ 推荐 |
| ARQ | asyncio 原生、轻量，功能少 | 小型项目可用 |

任务要幂等 + 可断点续跑（记录 `processed_chunks`），大文档失败重试不能从头来。

## 3. 三套组合方案

### 方案 A — 起步/验证版（1~2 周出可用系统）
```
FastAPI + MySQL8 + Milvus Standalone + Redis + Celery
百炼 text-embedding-v4 + gte-rerank-v2（云 API）
DeepSeek / Qwen（云 API，双通道）
Vue3 + Element Plus（vue-pure-admin）
docker-compose 单机
```
适合：先跑通全链路，快速验证效果。**不需要 GPU**，但必须能出网。

### 方案 B — 标准生产版（推荐）★  ← **本项目采用**
```
方案 A + MinIO + LiteLLM 网关 + Langfuse + Casbin
Milvus 独立数据盘 + 解析/向量化双队列 + milvus-backup
Nginx + HTTPS + 出网白名单（仅网关可出网）
```
适合：内网正式使用，50~500 人。详见 §6。

### 方案 C — 企业私有化版
```
Milvus 或 ES（千万级）+ K8s + vLLM 集群（本地 Qwen3）
OIDC/企业微信 SSO + 审计日志 + 全链路监控
```
适合：数据不出内网、大规模、有运维团队。

## 6.1 Milvus 落地要点（选它就必须提前知道这几条）

| 事项 | 做法 |
|---|---|
| 版本/资源 | Milvus 2.5+（2.5 起内置 BM25 function + `hybrid_search`，**不用再引 ES 做混合检索**）。8C16G 可跑，生产建议 16C32G + SSD |
| Collection 设计 | **一个 collection 装所有知识库**，用 `kb_id` 作 `partition_key` 或标量过滤字段。切勿"每库一个 collection"——collection 多了元数据服务压力大、加载慢 |
| 索引 | `HNSW(m=16, efConstruction=200)` + `COSINE`；超亿级再考虑 `IVF_FLAT` 省内存 |
| 过滤性能 | 必须 `partition_key = kb_id`，否则带权限/知识库过滤的检索会退化成全量扫描 |
| 混合检索 | dense（百炼 embedding）+ Milvus 内置 **BM25**，`RRFRanker(k=60)` 融合，再 `gte-rerank-v2` 精排 |
| 删除与更新 | Milvus 是**标记删除**，删文档后要触发 `compact`，否则空间不释放、检索仍可能命中脏数据 |
| 写入可见性 | 写入后默认在 growing segment，`consistency_level=Bounded` 下**立即查可能查不到**。上传后的"立刻提问"要加 flush 或延迟/轮询确认 |
| 备份 | `milvus-backup` 定期快照到 MinIO；MySQL 和向量库要**同时**备份，否则 `chunk_id` 会对不上 |
| 运维门槛 | etcd + MinIO + Milvus 三个容器，务必写进 compose 的 healthcheck 和启动顺序，否则第一次启动必失败 |

> 代价提醒：Milvus 比 Qdrant 重不少。你选它是为了规模和功能，那么**运维脚本、监控、备份**这三件事必须一并做，否则后期很容易踩坑。

> **混合检索实测结论（2026-11-02，P1.5）**
>
> 接入方式：`content` 字段开 `enable_analyzer=True` + `analyzer_params={"type":"chinese"}`，
> 配合 `FunctionType.BM25` 由 Milvus 自动生成 `sparse` 向量（**不需要自己算 BM25，也没有额外 API 费用**），
> 检索走 `hybrid_search` + `RRFRanker`。
>
> **三轮对比测试（5 条 / 23 条 / 20 条只差编号）结果：纯向量与混合检索均为 4/4，无可观测差异。**
> 原因是 `qwen3.7-text-embedding-flash` 对序号、型号、编号这类 token 的区分力远超预期，
> 连 `RACK-007` vs `RACK-008` 这种只差一位的都能分开。
>
> **那还要不要 BM25？要，但理由不是"提升效果"：**
> 1. **下限保护**：RRF 只融合排名不比分数，最差情况下等价于两路之一的水平，不会更差（实测一致）。
> 2. **规模效应**：20 条时 dense 靠近似就够；到几万切片、且存在大量同模板文档（台账、工单、条款）时，
>    向量空间会被同质内容挤压，字面匹配的价值才显现。
> 3. **更换模型时的保险**：不是每个 embedding 模型都有这么好的 token 级区分力。
> 4. **成本≈0**：稀疏向量由 Milvus 内部生成，无外部调用。
>
> 所以结论是「保留但不必期待立竿见影」，真正的效果拐点要靠万级真实语料来验证。
> 如果后续评测发现 dense 已经足够，可以把它降级为可选开关（`retrieve_config.hybrid=false`）。

### 6.1.1 混合检索接入时的三个坑

| 坑 | 现象 | 解法 |
|---|---|---|
| 字段缺 `enable_analyzer` | 建表报 `BM25 function input field must set enable_analyzer to true` | 字段参数必须同时给 `enable_analyzer=True` 和 `analyzer_params` |
| analyzer 用默认 `standard` | 中文按单字切分，BM25 形同虚设 | 必须 `{"type": "chinese"}`（jieba） |
| RRF 分数当余弦用 | 收集合里同时有 vector 和 sparse 后，纯向量 `search` 报 `multiple anns_fields exist`；且 RRF 分只有 0.01~0.05，用 0.2 阈值过滤会**全部过滤掉** | 纯向量检索显式传 `anns_field="vector"`；混合模式的阈值判断交给 rerank，不要用余弦阈值 |

## 6.2 全云 API 的代价与治理（三个前提 + 四项措施）

全云 API 让架构变简单了（不用 GPU、不用 Ollama、不用本地推理运维），但**性质变了**：知识库不再是"只在内网"的资产。这件事需要你明确知晓并认可。

### 6.2.1 出网范围（看清这两条再决定）

| 时机 | 外发内容 | 目的地 |
|---|---|---|
| 上传文档 → 切片 → 向量化 | **切片全文**（每个 chunk 的完整文本） | 阿里云百炼 |
| 用户提问 | 问题 + 检索命中的 top_k 片段 + 对话历史 | DeepSeek / 百炼（生成）· 百炼（rerank 传入 query+候选片段） |

⚠️ 也就是说：**只要上传了文档，内容就已经离开内网。** 这不再是"私有化部署"，准确叫法是「私有化运行 + 云端模型服务」。

### 6.2.2 三个必须确认的前提

1. **合规**：这批文档是否允许发送给第三方云服务？含客户信息、合同、身份证号、财务数据的库，通常不行。建议按知识库分级：涉密库禁入、一般库放行。
2. **厂商条款**：确认百炼和 DeepSeek 都开通了「数据不用于模型训练」的企业条款，并留存截图/合同。个人版 API 与企业版的条款不同，别用错。
3. **断供预案**：Embedding 一旦绑定百炼，切换 = 全量重建向量（成本 + 停机）。所以要么接受锁定，要么在设计上留好重建能力（见 6.5.5）。

### 6.2.3 四项治理措施（P1 就要做，不留到后期）

| 措施 | 做法 |
|---|---|
| **出口收敛** | 只有 LiteLLM 网关容器可出网，白名单仅放行 `dashscope.aliyuncs.com`、`api.deepseek.com`；api/worker/前端全禁 |
| **审计日志** | `llm_call_logs` 表记录：时间、用户、模型、场景（embed/chat/rerank）、token 数、耗时、状态、关联 doc_id |
| **敏感前置闸门** | 知识库级别 `sensitivity` 字段；涉密库直接禁止上传或强制走本地模型（保留扩展点） |
| **成本熔断** | Redis 累计当日 token，超过阈值告警/降级（降 top_k、禁 rerank），避免一次误操作跑爆账单 |

### 6.2.4 架构

```
内网 ─────────────────────────────────────────────────┐
                                                     │
 Vue3后台 ── FastAPI ── LangGraph ── LiteLLM 网关 ──[白名单出网]──┬─> 百炼（embed / rerank / qwen）
                  │         │                                   └─> DeepSeek（chat）
                  │         └─ Milvus（向量，本地）
                  ├─ MySQL / Redis / MinIO（本地）
                  └─ 审计日志 · 成本计数 · 限流熔断（Redis）
                                                     │
出网规则：仅网关容器可出网；只放行两个模型厂商域名；其余 DROP
```

> 想反悔也容易：LiteLLM 保留 OpenAI 协议入口，日后若要接回本地 vLLM/Ollama，只改网关上游配置，**业务代码零改动**。但已经用百炼生成的向量必须全量重建——这是不可逆的一次性成本。

## 6.5 模型接入落地要点（百炼 Embedding/Rerank + DeepSeek/MiMo 双通道）

### 6.5.1 对话模型：DeepSeek 与 MiMo 并行支持

| 维度 | DeepSeek（deepseek-chat） | MiMo | 工程影响 |
|---|---|---|---|
| 协议 | OpenAI 兼容 | **待确认**（需 OpenAI 兼容端点或单独 provider） | 见 6.7.3 |
| 上下文 | 128k 级 | 待确认 → 配置成 `max_context_tokens` | 不要写死在代码里 |
| 结构化输出 | 支持 `response_format=json_object` | 待确认 | 不支持时降级为「提示词约束 + 宽松解析 + 重试」 |
| tokenizer | 自有 | 自有 | **成本统计必须按模型分别计，不能混算** |
| 默认 max_tokens | 偏小 | 待确认 | 一律显式传，否则答案会"说一半就断" |

> MiMo 的具体参数我没有可靠依据，**不臆测**。接入当日用一组测试请求实测四项：最大上下文、是否支持 json_object、是否支持流式、单次 max_tokens 上限，然后把结果写进 `model_configs` 表。

**实现要求（双通道的代价，必须做，否则切换时炸）：**

1. Prompt 模板里**禁止出现任何厂商专有标记**（如 `<|im_start|>`、FIM 标记），只用标准 system/user/assistant 三段式。
2. 配置化：`model_configs` 表存 `provider / base_url / api_key(加密) / model / max_context / supports_json / enabled`；`knowledge_bases` 可覆盖（允许 A 库用 DeepSeek、B 库用 MiMo）。
3. 每次调用记录 `provider`、`model`、`prompt_tokens`、`completion_tokens` 到 `llm_call_logs`。
4. **切换模型前先跑回归集**：准备 30~50 条标准问答，切换后重跑，看引用准确率是否下降。没有回归集就别切——"感觉差不多"是最贵的错觉。

### 6.5.2 Embedding：百炼 `text-embedding-v4` 的四条硬约束

| 参数 | 值 |
|---|---|
| 模型 | **`qwen3.7-text-embedding-flash`**（实测可用，1024 维）；备选 `text-embedding-v4` / `v3` |
| 维度 | 支持 MRL 多档，**本项目取 1024**（flash 默认即 1024） |
| 单条上限 | 8192 token |
| 单次批量 | 最多 10 条文本（代码里 `batch_size` 做成可配置，默认 10） |
| 相似度 | COSINE（返回值已归一化） |
| 调用方式 | 百炼原生 SDK，或 OpenAI 兼容 `/v1/embeddings` |

**四条硬约束，对应四段必须写的代码：**

1. **batch ≤ 10** → 10 万切片 = 1 万次 HTTP 请求。必须做**并发池（5~10 并发）+ 令牌桶限流**，否则要么慢到受不了，要么撞限流。
2. **单条 ≤ 8192 token** → 超长必须**入库前预校验并截断**。注意：批内有一条超长可能导致**整批失败**，别让一条脏数据拖死一个任务。
3. **一定会有 429 / 5xx** → 指数退避 + 随机抖动重试（最多 3 次）；任务必须**按 `chunk_id` 幂等**，重跑时跳过已成功的切片，否则大文档失败一次就从头再来。
4. **维度一旦上线就锁死** → `knowledge_bases` 存 `embedding_model` / `embedding_dim` / `first_indexed_at`；改维度 = 全量重建。

**吞吐与成本（估算口径，别硬记数字）：**

- 吞吐：10 并发 × 每批 10 条，实际受账户 RPM/TPM 限制，10 万切片大约 **10~40 分钟**——比 CPU 跑本地模型快一个数量级，这是全云方案最实际的收益。
- 成本：按输入 token 计费，**一次全量入库 = 全部文档 token（约字数 × 1.3）**。需要特别注意：**重切分参数、换 embedding 模型、修 bug 重跑，都要再付一次全量费用**。所以切片参数在后台改完，要提示用户"将触发全部重建并产生费用"。

### 6.5.3 为什么定 1024 维而不是 2048

> **实测数据（2026-11-02，`qwen3.7-text-embedding-flash`）**
>
> | 环节 | 规模 | token 消耗 |
> |---|---|---|
> | 入库 | 8 个切片（603 字） | 500 |
> | 查询向量化 | 4 次 | 91 |
> | Rerank | 4 次 × 5 候选 | **1276** |
> | 合计 | — | **1867** |
>
> 检索准确率 4/4（4 个问题各自命中对应文档，向量分 0.62~0.70）。
> 整条链路成本不足 0.01 元量级，验证阶段完全不会超预算。
>
> **两个反直觉的实测结论：**
> 1. **不同 embedding 模型的 tokenizer 差异巨大**：同一句中文，flash 计 19 token，`text-embedding-v4` 只计 5 token。
>    所以比较成本不能只看"每千 token 单价"，要算 `单价 × 每字 token 数`。
> 2. **rerank 比 embedding 还贵**：rerank 的输入是 `query × 候选数`，5 个候选 4 次查询就烧掉 1276 token。
>    召回从 30 提到 100，rerank 费用直接翻 3 倍以上。**"多召回再精排"要克制**，30 条足够。

| 维度 | 效果 | 100 万切片的向量占用（float32） | 结论 |
|---|---|---|---|
| 2048 | 最好 | ≈ 8 GB + HNSW 图 | 除非效果不够，否则不必要 |
| **1024** | 差 1~2 分 | **≈ 4 GB + 图，实际占 5~6 GB 内存** | ✅ 效果/成本平衡点 |
| 512 | 再差 1~2 分 | ≈ 2 GB | 内存吃紧时降级方案 |

### 6.5.4 Rerank：百炼 `gte-rerank-v2`

- 接口形态：`TextReRank`，输入 1 个 query + N 个候选文档，输出每个候选的 `relevance_score`。
- 推荐链路：**向量+BM25 召回 top 30 → rerank → 取 top 5~8 喂给大模型**。召回少而精比堆 top_k 有效得多。
- 两个注意：① 候选数量控制在 50~100 以内，rerank 也按 token 计费且输入是 query×N；② 超长候选会被截断，切片过大时 rerank 效果会打折——这也是建议 chunk_size 别超过 512 的原因。
- 既然全云，rerank 用百炼和 embedding 同一家，**合规面不额外扩大**，还能共用密钥和限流配额。

### 6.5.5 供应商抽象层（这一步决定你将来能不能"下车"）

```
app/core/llm/
├── base.py                 # EmbeddingProvider / ChatProvider / RerankProvider 三个 Protocol
├── dashscope_provider.py   # 百炼：embed(v4) / rerank(gte-rerank-v2)
├── openai_compat.py        # DeepSeek、百炼兼容模式、未来 vLLM/Ollama 全走这里
└── registry.py             # 按配置实例化，业务层只 import registry
```

业务代码永远只调 `registry.get_embedding()`，不出现 `dashscope` 字样。这样：

- 今天最省事，全部云 API；
- 哪天要转私有化，**新增一个 provider 即可，业务层零改动**；
- 但已经入库的向量必须重建 —— 所以配一个重建工具：

```bash
python -m tools.reindex --kb-id 12 --to-model text-embedding-v4 --dim 1024
# 流程：读 MySQL chunks → 重新 embed（限流+幂等）→ 写入新 collection
#      → 校验条数一致 → 原子切换 collection alias → 旧 collection 保留 7 天再删
```

**这就是"供应商锁定"唯一的解药：不是避免绑定，而是保证能低成本重建。**

### 6.5.6 与 Milvus 混合检索怎么拼

```
用户问题
  ├─ 百炼 embed(query) ──────────────> dense 向量 ─┐
  └─ Milvus BM25（chinese analyzer）─> sparse 向量 ─┴─> hybrid_search + RRFRanker
                                                          ↓ top 30
                                              百炼 gte-rerank-v2 精排
                                                          ↓ top 5~8
                                              DeepSeek / Qwen 生成 + 引用标注
```

注意：用云 Embedding 后**没有 bge-m3 那种自带 sparse 输出**，稀疏那一路只能靠 Milvus 内置 BM25 function，所以 6.1 里提到的 `chinese` analyzer 配置是**必需项，不是可选项**。

## 6.6 对话历史与记忆（三层存储，别混在一起）

### 6.6.1 为什么要分三层

很多人把"历史记录"一股脑塞进一个表，结果三个问题同时爆：查会话列表变慢、多轮上下文被截断、调 RAG 时无法回放当时检索到了什么。分层后各司其职：

| 层 | 存哪 | 存什么 | 保留期 |
|---|---|---|---|
| **业务历史** | MySQL `chat_sessions` / `chat_messages` | 完整问答正文、引用、模型、token、耗时、用户反馈 | 永久（可归档冷表） |
| **编排运行态** | LangGraph Checkpointer（MySQL saver） | 图每一步的 State，支持中断续跑、回放调试 | 30 天滚动清理 |
| **短期上下文** | Redis | 最近 N 轮拼好的 prompt 片段 | 1~24h TTL |
| **检索快照** | MySQL（`chat_messages.retrieval_snapshot` JSON） | 当时命中的 chunk_id 列表 + 相似度分数 + rerank 分数 | 与消息同寿命 |

### 6.6.2 表结构草案

```sql
-- 会话
chat_sessions(
  id, user_id, tenant_id, title, kb_ids_json,
  chat_model, summary,          -- summary: 滚动摘要，见 6.6.3
  message_count, created_at, updated_at, is_deleted
)

-- 消息
chat_messages(
  id, session_id, seq, role,            -- user / assistant / system
  content,                              -- 正文
  citations_json,                       -- 引用：[{chunk_id, doc_id, page, score}]
  retrieval_snapshot,                   -- JSON：召回列表 + 各阶段分数
  model, prompt_tokens, completion_tokens, latency_ms, ttft_ms,
  feedback,                             -- like / dislike / null
  created_at
)
```

### 6.6.3 核心原则：存全量 ≠ 喂全量

- **落库**：所有消息永久保存，后台可查、可导出、可审计。
- **喂模型**：只取最近 **6~10 轮**；超出阈值时把最老的几轮压成 **200 字滚动摘要**，存回 `chat_sessions.summary`。

原因很实际：128k 上下文不代表该全塞。全塞会让 token 成本线性涨，还会触发"中间遗忘"（lost in the middle）——关键信息埋在长上下文中间，模型反而看不见。滑窗 + 摘要比堆上下文稳得多。

### 6.6.4 检索快照必须存（最容易被忽略的一条）

三个理由，缺一不可：

1. **调效果**：RAG 出问题，80% 是检索问题不是生成问题。没有当时的召回列表和分数，你无法判断是"没检到"还是"检到了但模型没用"——只能盲调。
2. **引用溯源**：前端点引用角标要定位原文；文档被更新/删除后，快照仍能展示当时的内容。
3. **合规审计**：能回答"这条答案依据的是哪份文档的哪一段"。

成本极低（一条 JSON 几 KB），价值极高。**这是 P2 就要做的，不要留到后期补。**

### 6.6.5 权限与归档

- 历史严格按 `user_id` 隔离；管理员可查但每次查询写审计日志。
- 删除用软删除（`is_deleted`），实体保留 30 天供审计后再物理清理。
- 容量：单轮约 2~8 KB，100 万轮 ≈ 2~8 GB，MySQL 完全扛得住；建议按 `created_at` 月度分区，远期归档冷表。
- 可选增强（二期）：跨会话长期记忆——把用户偏好、高频问题单独抽成 `user_memories` 表，问答时作为额外上下文注入。

### 6.6.6 另一类"历史记录"：操作审计

除了对话历史，后台还需要 **`audit_logs`**：谁登录、谁上传/删除文档、谁改了切片参数、谁调了模型配置、权限变更。

这不是可选项——切片参数一改会触发全量重建（见 6.5.2），**必须能查出"谁在什么时候改了什么"**。字段：`operator_id, action, target_type, target_id, before_json, after_json, ip, created_at`。

## 6.7 实施约束（由你的确认推导出的硬性要求）

### 6.7.1 权限模型（简化但不阉割）

| 角色 | 后台 | 前台问答 | 知识库管理 | 参数配置 | 用户管理 |
|---|---|---|---|---|---|
| `super_admin` | ✅ | ✅ | ✅ 全部 | ✅ | ✅ |
| `admin` | ✅ | ✅ | ✅ 被授权范围 | ✅ | ❌ |
| `user` | ❌ 403 | ✅ | ❌ | ❌ | ❌ |

- 前端：动态路由 + 菜单按权限下发；越权访问后台页面直接跳 403，**不只是隐藏菜单**。
- 后端：每个后台接口挂 `Depends(require_perm("xxx"))`，双保险。
- **知识库可见性仍要管**：普通用户虽然不进后台，但 A 部门的人不该看到 B 部门的库。所以 `kb_members` 表保留，角色简化两级：
  - `owner`：被邀请后可在**前台的知识库页**上传/删除文档、触发重建、邀请他人；仍不能进后台改全局参数。
  - `viewer`：只能检索和问答。
- 判定顺序（每个接口都要走）：`super_admin` 直通 → 全局角色权限 → 库级成员身份 → 默认拒绝。

> **实施变更（P0.5）：未引入 Casbin，改用表驱动 RBAC。**
> 原因：本项目是「3 个全局角色 + 库级 owner/viewer」，属于最简单的 RBAC。Casbin 的 adapter 会额外建一张
> `casbin_rule` 表，与已有的 `roles` / `permissions` / `user_roles` / `role_permissions` 功能完全重叠，
> 两套权限数据需要双向同步，是典型的 bug 源，且排查成本高。
> `app/core/rbac.py` 保持了 Casbin 风格的调用形态（`has_permission(sub, obj, act)`），
> 将来若要做多租户域隔离或 ABAC，替换该模块实现即可，业务层代码无需改动。
- 所有越权尝试写 `audit_logs`（含 IP），这是安全基线。

### 6.7.2 200MB 单文件的真实挑战（带宽不是问题，内存和超时才是）

**先说数字，你可能需要调整这个上限：**

| 场景 | 切片数 | 一次全量 embedding 费用（量级） |
|---|---|---|
| 万级切片（2 万 × 512 token ≈ 1000 万 token） | 2 万 | **约 5 元** |
| 单个 200MB 纯文本（≈1 亿字符 ≈ 1.5 亿 token） | **约 30 万** | **约 75 元** |
| 单库 1GB 装满文本（≈7.5 亿 token） | 约 150 万 | **约 375 元/次重建** |

👉 **「万级切片」和「200MB 单文件」差了两个数量级**，这两个约束同时存在时，实际规模由文件决定，不由你估的「万级」决定。建议在后台加载文件时**先预估切片数和费用再做确认**，而不是盲目入库。

**工程上必须做的六件事：**

| 问题 | 不做的后果 | 做法 |
|---|---|---|
| Nginx 默认 `client_max_body_size 1M` | 上传直接 413，前端只报"网络错误" | 调到 `210M`，并配 `client_body_timeout 600s` |
| `await file.read()` 读进内存 | 200MB × 并发数 → 容器 OOM | 流式分块写入 MinIO（8MB/块），**全程不进内存** |
| PyMuPDF 打开 200MB PDF | 峰值内存 500MB~2GB | 单独「大文件队列」+ 专用 worker（并发=1、`max_memory_per_child`） |
| 解析超时 | worker 卡死、队列堵住 | `task_time_limit=1800s` + soft_time_limit 提前告警 |
| 解析中断要重来 | 用户等 20 分钟后失败 | 按页/按章节记录 `processed_pages`，支持断点续跑 |
| 扫描版 PDF | **上传"成功"但切片为 0，用户以为能用** | 解析后校验文本量，低于阈值直接标 `no_text_layer` 并明确提示"该文件无文本层，需 OCR（当前未支持）" |

**这条最容易被忽略**：不做 OCR 的情况下，扫描件不会报错，只会安静地产生零切片。必须在上传后给用户明确反馈，否则是"看起来成功、实际不可用"的坑。

### 6.7.3 MiMo 接入要求

MiMo 走的是同一套 OpenAI 兼容抽象，但接入前需要确认：

| 项 | 要求 | 不满足时 |
|---|---|---|
| 端点 | 提供 `base_url` + `api_key` + `model` 名 | 用官方 SDK 则需单独写一个 provider |
| 结构化输出 | 最好支持 `response_format={"type":"json_object"}` | 引用校验降级为「提示词约束 + 宽松 JSON 解析 + 失败重试」 |
| 上下文长度 | 需知道上限，配置成 `max_context_tokens` | 超长时按 6.6.3 的滑窗+摘要自动裁剪 |
| 流式 | 支持 SSE | 不支持则前端退化为整体输出 |

切换记入 `chat_messages.model` 与 `llm_call_logs.provider`，便于 A/B 对比同批问题的回答质量。

### 6.7.4 「精致稳定完善」的验收标准（这是可检验的，不是形容词）

| 维度 | 具体标准 |
|---|---|
| **错误处理** | 统一错误码 + 中文提示；前端永远不看到 Python 堆栈；每个错误有 `trace_id` 可查 |
| **全链路超时** | 上传 600s、解析 1800s、embedding 30s、LLM 首 token 30s、总时长 120s，逐跳设置 |
| **幂等** | 重复上传同一文件不产生重复切片；任务重跑跳过已完成（按 `chunk_id` / `page_no`） |
| **数据一致性** | 入库后校验 `MySQL 切片数 == Milvus 实体数`，不一致标红并告警 |
| **可观测** | `trace_id` 贯穿前端→API→Celery→模型调用；Langfuse 记录每次检索与生成 |
| **前端体验** | 骨架屏、空态、错误态、上传进度条、任务进度轮询、引用角标可点开原文 |
| **安全** | 密码 bcrypt、登录限流、JWT 黑名单、后台接口双鉴权、越权写审计 |
| **测试** | pytest 单元 + 接口测试；一条 `smoke.sh` 冒烟脚本（登录→建库→上传→问答） |
| **交付物** | OpenAPI 文档、部署手册、运维手册（备份/恢复/扩容） |
| **备份** | MySQL 每日逻辑备份；Milvus `milvus-backup`；MinIO 版本化；三者时间点对齐 |

## 6.8 提示词管理（P5，已实现）

系统提示词不能硬编码在代码里。一旦上线，改一句"不要输出套话"都要发版，而这类改动往往是运营/业务方提的需求。

### 6.8.1 为什么单独建表，不放进 system_settings

`system_settings` 是全局 KV，表达不了两件事：

| 需求 | KV 的问题 |
|---|---|
| **按知识库覆盖** | 同一 code 在不同 kb 各一份，KV 只能存一个值 |
| **版本与回滚** | 提示词是效果最敏感的配置，改坏后必须能一键回退；KV 只留最后一版 |
| **归因** | 要在 `llm_call_logs` 里记 `prompt_version`，才能事后分清"是换了模型还是改了提示词" |

表：`prompt_templates`（当前生效）+ `prompt_versions`（每次保存的快照）。

### 6.8.2 三份内置模板

| code | 用途 | 触发时机 |
|---|---|---|
| `system_qa` | 基于资料回答、标注引用 | 检索到资料的常规问答 |
| `direct_answer` | 寒暄/无关问题的礼貌回复 | 意图路由判定无需检索 |
| `query_rewrite` | 多轮追问补全指代 | 有历史且问题很短时（图内判断） |

### 6.8.3 五个容易踩的实现点

1. **变量语法用 `{{name}}`，不用 `{name}`**。提示词里经常出现 JSON 示例（`{"a": 1}`），单花括号会让 `str.format` 抛 `KeyError: 'a'`，而报错信息完全看不出是哪段提示词的问题。
2. **保存时校验变量白名单**。`{{contxt}}` 拼错不会报错，只会把字面量发给模型，表现为"回答质量莫名下降"——这是最难排查的一类故障。
3. **`kb_id=0` 表示全局，不用 NULL**。MySQL 唯一索引对 NULL 不去重，会存出多条"全局"记录且不报错。
4. **回滚 = 旧内容作为新版本提交**，不覆盖历史；版本号取「模板行」与「历史表」的 max+1。否则删过行再保存会撞唯一键（`Duplicate entry`），而报错信息看不出是版本号问题。
5. **读失败必须回退内置默认**。数据库抖动、迁移没跑，都不该让整个问答功能不可用。

### 6.8.4 缓存策略

进程内 30s TTL + 写操作按 code 整体失效。**不做按 kb 的精细清理**：写操作一天几次，而漏清一条缓存会造成"改完提示词没生效"这种极难自证的问题。多进程部署时各进程独立缓存，30s 内可能短暂不一致，对提示词可接受。

### 6.8.5 后台能力

预览（不花钱，只渲染）、试跑（真实调模型，可带知识库检索）、版本历史、回滚、恢复默认、审计留痕。恢复默认采用「写回内置内容并版本+1」而不是删行，这样"谁在何时恢复了默认"仍可查。
